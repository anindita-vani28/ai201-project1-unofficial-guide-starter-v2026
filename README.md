# Unit 1

## What This Does

This project indexes the `campus_life` corpus and answers questions about dining, housing, coursework, library hours, and campus logistics. It retrieves relevant chunks from the corpus, checks whether the best match is close enough to answer, and then generates a grounded answer that names at least one source document.

The system is designed for concise, campus-focused questions where the answer is present in a short document or paragraph rather than in a long narrative.

## Chunking Strategy

**Chunk size:** paragraph-based chunking, not a fixed 800-character window

**Overlap:** none

I used paragraph boundaries for this corpus because the documents are short, fact-like posts and many of them are only a few sentences long. A fixed-size chunker would split these into fragments that lose meaning. The custom `split_documents` function in `chunker.py` breaks on blank-line paragraph boundaries and merges a very short leading paragraph into the next paragraph when needed so that the chunk still reads like a complete thought.

This fits the campus documents better than a fixed window because the useful information is often contained in a single paragraph rather than across a long character span.

## How I Used AI

**1.** I asked for help choosing a retrieval cutoff based on distance distributions, and the model suggested comparing the best distances for in-corpus vs. out-of-scope questions. I used that idea to check the actual numbers, and I kept the threshold at `0.6` because it cleanly separated the two groups.

**2.** I asked for feedback on the paragraph-merging logic in `chunker.py` after noticing that short intro paragraphs were getting split off from their main content. The model suggested merging a very short leading paragraph with the next paragraph; I implemented that logic directly in `split_documents` so the chunks read as complete thoughts.

**3.** In unit 2, I asked AI to audit my evaluation against the rubric. It identified that my original write-up repeated the same numbers before and after, did not record response times, and called an unchanged cutoff an improvement. I used that feedback to add an auditable scorer and timing data, preserve failed API calls in the run logs, and report the unsuccessful retry experiment instead of claiming it worked.

## Verdicts

| # | Verdict | How I decided |
|---|---|---|
| 1 | MET | In every run, all five retrieval result sets contained the phrase committed in `questions.py`; 5/5 exceeds the 4/5 target. |
| 2 | MISSED | The target requires 5/5 answers to name a source. The provider returned errors instead of answers on all 15 attempts, so every run was 0/5. |
| 3 | MET | The gate refused all five out-of-scope questions at the fixed 0.6 cutoff; 5/5 exceeds the 4/5 target. |
| 4 | MET | All five sampled chunks were independently understandable; 5/5 exceeds the 4/5 target. |
| 5 | MISSED | None of the 15 attempts returned an answer. An error received in under 10 seconds does not satisfy a target that specifically requires an answer. |

## Diagnoses

Criteria 2 and 5 failed at the **generation stage**, not loading, chunking, embedding, retrieval, or gating. The evidence separates the stages cleanly: every expected fact was present in the retrieved chunks, all five in-scope distances passed the gate, and the generation request then received `503 UNAVAILABLE` from `gemini-3.5-flash-lite`.

The mechanism was temporary provider capacity. `generate.py::generate` retried 429 rate-limit responses but immediately raised other errors, including the observed 503. That left the system unable to turn correct retrieved context into an answer, which simultaneously caused the missing-source and response-time misses. The earlier log at [`results/run_2026-09-21_1615.md`](results/run_2026-09-21_1615.md) contains 15 correct generated answers, which supports this diagnosis: the corpus, retrieval, grounding prompt, and API key had all worked previously.

## The Improvement

**What I changed:** I changed `generate.py::generate` so that HTTP 503/`UNAVAILABLE`/“high demand” responses use the existing bounded retry loop. A request now gets at most four attempts, with 1-, 2-, and 4-second exponential backoff. I also stopped the loop from sleeping after its final attempt.

**Why I picked it:** Every miss had the same mechanism: correct retrieval followed by a transient 503 at generation. Retrying that specific transient failure directly addresses the observed problem without changing the corpus, chunking, model, retrieval settings, cutoff, or prompt.

**Did it help?**

No. The change behaved as designed—each request made four attempts—but none of the 60 attempts returned an answer. First-run elapsed times became 13.63s, 11.12s, 7.68s, 8.71s, and 12.31s. Two failures ended in under 10 seconds, but failures are not answers, so Criterion 5 remained 0/5. Later attempts also encountered the free-tier quota after the retries increased request volume. The improvement therefore traded more waiting and quota use for no measured reliability gain during this outage.

Representative output from `generate.py::generate` after the change:

```text
[temporary service error] retrying in 1s (attempt 1 of 4).
[temporary service error] retrying in 2s (attempt 2 of 4).
[temporary service error] retrying in 4s (attempt 3 of 4).
ERROR: RuntimeError: The model service was still unavailable after 4 attempts.
```

## What's Still Broken

Criteria 2 and 5 are still missed because the generation provider returned no answers. My next step would be to wait for the provider outage to clear and rerun the unchanged after-test. If quota errors remain, I would make a later, separately measured change that paces against the observed free-tier limit of 15 requests per minute and honors the provider's requested retry delay.

I stopped here because this unit permits only one system improvement. Changing the model, changing the request limit, or adding another fallback now would combine multiple interventions and make it impossible to attribute the result to the 503 retry change.

## What I'd Do Differently

I would rewrite Criterion 5 to say: “For at least 4 of 5 questions, the system returns a **successful, sourced answer** within 10 seconds, measured end to end with caching off.” The original wording did not explicitly say how errors should count or define the measurement boundary. The revised wording preserves the same target while making those decisions unambiguous.
